# Risk acceptance and release enforcement

The owner-selected policy blocks every high/critical vulnerability and authentication, authorization or required-audit failure, including existing findings. Medium findings have a 30-day remediation deadline from verified first discovery; low findings have 90 days. Missing discovery dates require triage and block evaluation rather than starting a fresh clock on each scan. License findings remain separately visible; the owner has not prohibited MPL licenses. Required quality gates remain in force. Web/API DAST is deferred by owner decision and is recorded as deferred, never passed.

Operational failures cannot be excepted. Authentication failures, missing scopes, unavailable or stale reports, incomplete scans, invalid candidate identity, expired qualification and failed archival always block publication. A source scan is reusable only for the exact revision, trusted full-analysis context, required languages/configuration and a maximum age of 24 hours. PR-only CodeQL and Sonar new-code views do not establish the full baseline. Original reports, including dismissed/accepted findings and historical fixed states, are retained privately.

## Propose and approve

Create `docs/security/risk-acceptances/RA-0001.md` using the template below. Use one stable identifier per decision. The first document section is JSON inside `---` front matter, followed by human-readable reasoning. Each finding requires an exact report `scope` plus scanner, finding, component and version; missing scopes, unknown scopes and wildcards are rejected. The scope is part of the authenticated content and approved scope hash. An exception for `source:npm:tests/e2e` cannot waive the same advisory/package/version in `image:veyport`, another image or another source manifest. Add each intended scope explicitly and obtain renewed owner approval when adding or moving scopes.

Allowed report scopes are `source:go:hub`, `source:go:agent`, `source:go:cli`, `source:go:proto`, `source:go:infra/application-access/fixture`, `source:npm:web`, `source:npm:tests/e2e`, `source:pip:infra/audit-lab/storage`, `source:sast:sonar`, `source:sast:semgrep`, `source:sast:codeql`, `image:veyport`, `image:audit-ingest`, `image:audit-export`, `native:grpc` and `native:ssh`.

False-positive and not-affected assessments remain distinct from accepted real risk. Every temporary exception has an explicit expiration, no more than 90 days after its proposed approval time. Extensions require a new exact-content approval and may not waive a scanner outage.

Compute SHA256 of the entire Markdown file, including its reasoning and line endings. The owner reviews the exact revision/hash and manually dispatches **Approve exact security exception** (`risk-approval.yml`) on `main`, with the record ID, exact commit and exact file hash. The protected `ssdf-risk-approval` environment must require owner `lorconksu` (GitHub user ID `13374789`), allow only branch `main`, and allow sole-maintainer self-review. Review and approve that environment deployment. Preparing/scanning automation must never dispatch or approve this workflow.

The workflow fetches only record data; it never executes the record revision. It checks the owner’s authenticated initiating and triggering identities, first workflow attempt, trusted default-branch history and workflow/helper contents, environment configuration, exact record hash, scope, proposal time and expiry. The proposed approval time must precede dispatch by at most 24 hours. Its `ssdf-approval-RA-0001` artifact contains `approval.json`; copy that disclosure-safe descriptor to `RA-0001.approval.json` beside the record. Copying or editing a descriptor alone does not grant approval: release evaluation fetches the successful authenticated workflow run and its original artifact and requires an exact match.

Reruns do not create approvals or renew expiry. Changed content, expanded scope, changed expiry, expired records, deleted approval evidence, changed trusted approval implementation or revoked environment protection invalidate the approval. Delete the companion descriptor to revoke a decision in the next reviewed source revision; cancel/delete the originating run or its artifact for immediate invalidation. Recheck approved records immediately before registry publication and again before release assets are created. Each scanner’s independent finding needs its own matching scope.

GitHub cannot distinguish an owner UI dispatch from a dispatch using that same owner’s personal token. The mechanism authenticates the owner account and protected manual environment action; it does not claim human presence against compromised owner credentials or repository-administrator authority. Scanner jobs have no Actions write permission, and their automation identities cannot act as the owner. The owner’s personal approval credentials must not be provisioned on scanner/collector services.

## Bootstrap and private rehearsal

Approvals remain unavailable until the trusted workflow/helper exist on default branch `main`, the protected environment is configured, and the exact owner action succeeds. A feature-branch workflow, an approver-name string, dashboard dismissal or fabricated descriptor is never a bootstrap substitute. This PR creates no approved exception.

Use the existing **Staging Build** workflow with `prototype=true`, `publish=false`, a feature branch, an exact prototype version and `prototype-ssdf.N` tag input to rehearse privately. This builds and scans once, sends only recipient-encrypted candidate/evidence artifacts, requires the isolated candidate’s signed gRPC/SSH qualification and waits for a durable signed NAS receipt. Publication steps are disabled. Missing operational evidence remains a failed rehearsal. The legacy direct mutable `:staging` build/push is disabled; normal staging must consume an exact qualified published release.

The collector and coordinator require independent pinned public keys and scoped service credentials. Missing keys, collectors, full baseline analyses or deployed candidate checks block qualification. A source-built protocol fixture is useful test evidence but cannot claim that installed candidate bytes passed native qualification.

## Disclosure and retention

Records in this public repository contain only disclosure-safe rationale and opaque references such as `evidence:review-1`. Keep report locations, internal inventories, exploit details, tokens, signed URLs and request/response transcripts in the private archive. No sensitive data belongs in workflow inputs, approval artifacts or public release attachments. Publication attaches binary hashes/manifests and a fixed public summary; detailed candidate reports remain encrypted.

Published-release evidence is retained for one year from publication; other attempts for 180 days from completion, including failures and cancellations. The collector’s independent reconciliation records final outcomes and missing evidence when a cancelled workflow’s finalizer cannot run. Shared payloads remain protected through every live consumer’s retention period. GitHub’s seven-day encrypted transfer window is a retry deadline, not durable retention. Failure to obtain an authenticated receipt for the exact complete manifest prevents publication and temporary evidence cleanup.

## Source coverage policy review

The same manual workflow accepts separate `CR-NNNN` coverage-review records under [coverage-reviews](coverage-reviews/TEMPLATE.md). These authenticate an exact private inventory of scanner configuration, source exclusions and inline suppression annotations. Missing coverage-policy approval sets `coverage_complete:false`; vulnerability exceptions cannot waive it. The review does not invent security findings for quality annotations, classify unknown exclusions as false positives, or approve actual suppressed findings. Those findings still require their own scoped risk records. No baseline coverage review has been approved by this implementation.

The 30/90-day evaluator requires durable discovery dates. Snyk CLI output currently lacks verified first-discovery timestamps, and this implementation does not establish a durable historical finding ledger or substitute advisory publication dates. Medium/low vulnerability findings without that evidence remain blocked pending a trustworthy history integration or explicit triage that establishes their original dates; a new scan never resets the clock.

## CI evidence and current operating limits

Each report-producing CI job encrypts its available structured outputs and sanitized diagnostics to the archive recipient before upload. The collector independently discovers the fixed per-job artifacts, validates source/workflow/run identity, reconstructs retained report parts and archives each job closure. Cancellation does not depend on an aggregate finalizer. Missing chunks or unavailable provider outputs remain explicitly partial. The collector also recovers bounded, sanitized completed-job logs for early failures and cancellations.

Ordinary PR/main Semgrep remains a required CI gate. Release/prototype callers explicitly defer that same gate to the delivery job, where it runs once with the same version, rules and existing check before private baseline evaluation. Exporting provider results does not rerun Sonar or CodeQL. Plaintext Semgrep, Gitleaks, source-vulnerability and browser diagnostic artifact uploads are replaced by encrypted chunks. Existing coverage artifacts used by Sonar retain their current consumer path and are additionally archived encrypted; they remain an explicit existing public artifact surface pending a separate safe-consumer review.

Retained diagnostics redact authentication fields, tokens and browser resources that could contain session state; metadata distinguishes the original source fingerprint from the retained, reconstructable redacted content. Bounded collection failures remain failures with explicit missing output, never clean scans. Complete publication acknowledgements require all fourteen required same-run CI job closures, their authenticated terminal outcomes and the exact delivery manifest. A source-built fixture does not satisfy the deployed-candidate gate.

The archive/coordinator read-and-status credential is not provisioned yet, and unattended collection, qualification acknowledgement and automatic cleanup remain disabled. The owner will supply a narrowly scoped repository credential later. Deletion uses a separate identity and remains contingent on durable acknowledgement and completion of all artifact consumers. There is no live authenticated GitHub handoff claim from local cryptographic tests. Snyk first-discovery history enrichment and source-platform migration remain incomplete; the current policy blocks missing metadata and preserves the existing scanners and Dependency-Track integration.
